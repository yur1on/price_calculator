## Краткий вывод

Главный подтверждённый источник разрастания URL — обычные `<a href=".../book/?slot=...">` для **каждого** доступного времени в месячном календаре. `/book/` не закрыт `robots.txt`; ответ с действительным `slot` содержит `meta robots="noindex, nofollow"`, но робот должен сначала запросить этот URL, чтобы увидеть директиву. Таким образом, `noindex` предотвращает индексацию содержимого, но не расход обхода. Нельзя приписать этому механизму все 229 703 или 124 264 адресов без экспорта примеров Search Console, но форма URL из вопроса точно генерируется текущим шаблоном.

Сохранить публичные маршруты `/slots/` и `/book/`, но в отдельном согласованном изменении заменить ссылки на слоты HTML-формой с кнопками POST и CSRF. Промежуточный POST лишь выбирает слот и показывает форму клиента, финальный POST создаёт бронь после тех же серверных проверок. Это работает без JavaScript и не создаёт отдельный HTML-`href` для каждого времени. Старые GET-ссылки следует оставить работоспособными для пользователей с закладками и существующих интеграций; не делать массовую переадресацию всех `slot` на календарь.

## Robots, sitemap, canonical и GET-дубликаты

**Подтверждено по репозиторию:**

- `core/urls.py:29-46` формирует `/robots.txt`: `Allow: /`, запреты `/admin/`, `/master/`, `/payments/`, `/repairs/*/slots/`, и `Sitemap: <текущий origin>/sitemap.xml`. Явного запрета `/book/` нет. Шаблоны `slot_select.html`, `booking_form.html`, `booking_success.html` задают `noindex, nofollow`; базовый `repairs/templates/repairs/base.html:26` задаёт `index, follow` по умолчанию. Для индексируемых страниц `noindex` не обнаружен. В исходниках Django нет установки `X-Robots-Tag`; ответ прокси/CDN в production не проверен. Нельзя блокировать `/book/` в robots как единственную меру: заблокированный URL робот не сможет открыть и прочитать `noindex` ([Google Search Central](https://developers.google.com/search/docs/crawling-indexing/block-indexing)).
- `core/urls.py:46` и `repairs/sitemaps.py` обслуживают `/sitemap.xml`. В sitemap перечислены статические страницы, категории `/repairs/?cat=...`, пары бренд/категория `/repairs/<brand>/?cat=...`, модели `/repairs/<brand>/<model>/` и новости. Календарей, `book/?slot=...` и страниц успеха в sitemap **нет**. Страницы отдельных услуг `/repairs/<brand>/<model>/<service>/...` намеренно не являются отдельными страницами с описанием услуги, а маршруты `/slots/` и `/book/` — шаги записи.
- `repairs/templates/repairs/base.html:28` строит canonical как `request.scheme://request.get_host() + request.path`, без любых GET-параметров. `home.html` оставляет `/`; `brand_list.html:7` и `model_list.html:7` переопределяют canonical с нормализованным `?cat=<selected_cat>`; `repair_list.html` использует canonical без параметров. Таким образом, у страниц брендов и категорий canonical есть. Но все `?slot=` варианты `/book/` объявляют canonical на голый `/book/`, который без `slot` по `repairs/views.py:785-787` редиректит на календарь. Это слабый/противоречивый сигнал; `noindex` остаётся основным сигналом исключения. Проверить фактические canonical на production, включая схему и хост за reverse proxy.
- `repairs/views.py:423` `brand_list` и `:470` `model_list` принимают `?cat=`; недопустимые значения тихо показывают `phone`, без редиректа. `model_list` также принимает `?view=grid|list`, произвольный `?q=` и `?page=` (формы и ссылки в `repairs/templates/repairs/model_list.html:278-354`), но canonical всегда указывает только на `?cat=` — в том числе для страниц 2+ с другим набором моделей. На главной `?cat=` меняет список брендов, а `home.html:4` сохраняет canonical `/`. `slot_select` принимает `?month=`: неверное значение заменяется текущим месяцем, а месяц за пределом будущего горизонта прижимается к предельному без смены URL. Эти варианты увеличивают пространство обхода; доля в цифрах Search Console не доказана.
- `repairs/templates/repairs/base.html` доступен и мобильной, и десктопной вёрстке; отдельных шаблонов календаря для мобильного нет. `repairs/tests.py:423-459`, `repairs/test_seo.py` и `crm/tests/test_capacity.py:331-346` проверяют часть canonical/robots/sitemap и ограниченное число SQL-запросов, но не проверяют отсутствие обходяемых `href` слотов или согласованность canonical страниц 2+.

Для `129` «дубликатов без указанного canonical» нельзя назвать конкретные пути без списка из Search Console. В проверенных Django-шаблонах каталога canonical есть, поэтому нужно сравнить примеры GSC с фактическим HTML/HTTP-ответом: это могут быть другие endpoints, старые версии, ответы 3xx/ошибок, некорректный домен или URL, где бот не получил HTML. Каноникализация является подсказкой, а не гарантией выбора Google ([Google Search Central](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)).

## Автоматические тесты для будущего изменения
